# 배포

Ubuntu Server에 올리는 방법이다. 앱은 서버의 `127.0.0.1`에만 열리고, 외부에서는 SSH 터널로 접속한다.

배포 방법은 두 가지다: **Docker Compose**(§0) 또는 **systemd 직접 설치**(§1~§7). 접속(§5)과 운영(§7)은 같다.

## 0. Docker Compose로 배포

Docker가 이미지 안에서 빌드하므로 서버에 Node.js를 설치하거나 `npm ci`를 실행할 필요가 없다.

```bash
git clone <REPO_URL> /opt/rss-discord-bridge
cd /opt/rss-discord-bridge
cp default.env.example .env          # 키 등 값 채우기
mkdir -p data && sudo chown 1000:1000 data   # 컨테이너의 node 사용자가 쓸 수 있게

docker compose up -d --build
docker compose ps                    # STATUS가 healthy인지 확인
```

- **접속:** systemd 배포와 같다. 서버의 `127.0.0.1:8080`에만 열리므로 SSH 터널로 접속한다(§5).
- **포트 변경:** `.env`의 `PORT`만 바꾼다. 호스트 포트와 컨테이너 포트가 함께 바뀐다. 둘을 다르게 두면 관리 화면의 저장 요청이 Origin 검사에서 거부된다.
- **데이터:** DB는 `./data`에 남는다. 컨테이너를 지우거나 다시 만들어도 유지된다. 백업은 `docker compose stop` 후 `data/`를 복사한다.
- **업데이트:** `git pull && docker compose up -d --build`
- **로그:** 앱 오류는 `docker compose logs -f`, 수집·발송 결과는 관리 화면 `/logs`.
- **종료:** `docker compose stop`은 진행 중인 발송을 최대 60초 기다린다(`stop_grace_period`). 앱의 종료 대기는 기본 30초다. `SHUTDOWN_TIMEOUT_MS`를 늘리면 `stop_grace_period`도 앱 대기 시간보다 최소 30초 길게 조정한다.

> `docker run`으로 직접 실행하면 바깥에 열리지 않도록 기본값이 loopback이다. Compose 파일을 쓰는 것을 권장한다.

이미지는 GitHub Actions의 `CI` 워크플로가 Push마다 빌드하고, Compose로 띄워 상태 점검·loopback 포트·비root 실행·정상 종료까지 확인한다. 레지스트리에는 올리지 않는다.

**직접 설치 전에 알아 둘 것**
- **`npm ci`는 반드시 배포 서버에서 실행한다.** `better-sqlite3`는 OS별로 빌드되는 모듈이라 다른 컴퓨터의 `node_modules`를 복사하면 동작하지 않는다.
- **`.env`와 DB 경로는 실행 위치 기준이다.** systemd의 `WorkingDirectory`를 앱 폴더로 정확히 지정한다.
- **API 키는 `.env`에만 둔다.** 키가 없어도 앱은 시작하고, 번역만 꺼진다.

## 1. 설치

```bash
# Node 20 이상
curl -fsSL https://deb.nodesource.com/setup_20.x | sudo -E bash -
sudo apt-get install -y nodejs build-essential python3 git

# 전용 계정과 코드
sudo useradd --system --create-home --home-dir /opt/rss-discord-bridge --shell /usr/sbin/nologin rssbridge
sudo -u rssbridge git clone <REPO_URL> /opt/rss-discord-bridge
cd /opt/rss-discord-bridge

# 의존성과 빌드
sudo -u rssbridge npm ci
sudo -u rssbridge npm run build
```

## 2. 설정

```bash
sudo -u rssbridge cp default.env.example .env
sudo -u rssbridge mkdir -p data
sudo chmod 600 .env
```

`.env`에는 최소한 다음 값을 넣는다. 한 줄에 `KEY=value`만 쓰고, 줄 끝 주석은 쓰지 않는다(systemd가 읽지 못한다).

```ini
NODE_ENV=production
HOST=127.0.0.1
PORT=8080
PRIMARY_MODEL_API_KEY=
FALLBACK_MODEL_API_KEY=
```

나머지 값은 [구조.md §9](구조.md#9-설정값)에 있다.

## 3. 실행 확인

```bash
sudo -u rssbridge env NODE_ENV=production node dist/server/main.js &
sleep 2
curl -s http://127.0.0.1:8080/healthz   # {"status":"ok"}
curl -s http://127.0.0.1:8080/ready     # {"status":"ready"}
kill %1
```

## 4. systemd 등록

```bash
sudo cp Docs/rss-discord-bridge.service /etc/systemd/system/
# ExecStart의 node 경로가 `which node`와 같은지 확인한다
sudo systemctl daemon-reload
sudo systemctl enable --now rss-discord-bridge
sudo journalctl -u rss-discord-bridge -f
```

## 5. 접속

관리자 컴퓨터에서 터널을 연 뒤 브라우저로 `http://localhost:8080`에 접속한다.

```bash
ssh -L 8080:127.0.0.1:8080 <user>@<server>
```

## 6. 업데이트

```bash
cd /opt/rss-discord-bridge
sudo -u rssbridge git pull
sudo -u rssbridge npm ci
sudo -u rssbridge npm run build
sudo systemctl restart rss-discord-bridge
```

- **새 마이그레이션이 있는 업데이트:** DB를 백업한 뒤 적용한다.
- **2026-10-18 이전에 만든 DB:**
  1. 관리 화면에서 Export로 설정을 받는다.
  2. 서비스를 멈추고 `data/rss-discord-bridge.sqlite`(`-wal`, `-shm` 포함)를 지운다.
  3. 서비스를 다시 시작한 뒤 Import로 설정을 되살린다. 웹훅 URL은 다시 입력한다.

## 7. 운영

- **백업:** `data/rss-discord-bridge.sqlite`와 `-wal` · `-shm` 파일. 서비스를 멈추고 복사한다.
- **DB 파일 크기:** 큰 삭제 뒤에는 자정 정리 때 자동으로 줄어든다. 줄이는 동안(보통 수 초) 수집·발송이 잠시 멈춘다.
- **로그:**
  - 수집·발송·번역 결과는 관리 화면 `/logs`에서 본다(30일 보존).
  - 앱 오류는 `journalctl -u rss-discord-bridge`로 본다.
- **외부 공개:** `HOST`를 바꾸지 말고, 앞에 nginx 같은 리버스 프록시를 두고 TLS와 인증을 따로 구성한다.
- **포트 변경:** `.env`의 `PORT`를 바꾸고 재시작한다. SSH 터널 포트도 함께 바꾼다.
